# 求职工作台：产品约定与旧代码复用审查

本约定来自用户本轮问答，优先于此前通用代码执行工作台的第一版范围。当前只完成设计审查，不代表求职功能已实现。保留长期通用平台目标，以求职场景验证第一版。包版本暂不改变。

## 第一版成功标准

1. 少翻聊天记录：从岗位详情直接找到相关简历、邮件、关键决定、下一步和信息来源。
2. 不错过跟进：明确截止日期、面试邀请和未回复事项形成待办与提醒；后台状态和失败可见。
3. 清楚岗位进度：状态有依据，区分事实、建议和待确认事项；填好申请不等于已投递。

这些标准优先于 agent 数量、代码执行、通用插件和框架建设。

## 已确认产品行为

| 主题 | 约定 |
|---|---|
| 入口 | 一个持续对话的 Master，聊天与看板并排；选中岗位后带入对应背景，无需重新解释 |
| 首页 | 今日待办与截止日期、岗位阶段、匹配度与推荐理由；审核操作进入相应岗位或待办，避免再堆独立大面板 |
| 阶段 | 待考虑、准备中、已投递、面试、结束；状态不明单独标记；结束原因保留 |
| 档案 | 导入简历，通过聊天补充目标岗位、地区、薪资、工作资格等，区分硬性要求与偏好，由用户确认修改 |
| 信息来源 | 用户提供岗位链接 + 主动发现岗位；LinkedIn、Indeed 是优先发现入口，实际申请网站可能不同 |
| Gmail | 首次整理最近三个月的求职相关邮件；读取整理，不发信、不删除、不修改邮箱内容 |
| 旧资料 | 将旧 Codex 对话整理成可审核导入清单；已确认投递与状态不明分开，两种来源合并去重，不凭猜测补全 |
| 日常主动性 | 整理邮件、更新内部看板、推荐今日行动，准备简历修改、面试训练和申请材料 |
| 审核边界 | 读取分析、生成草稿、更新内部看板可自动；对外发信和修改外部资料先审核；申请辅助填写，用户检查并亲自点击提交 |
| 通知 | Windows 本机后台，上午 10 点一份简报；错过则下次启动补发当天一份，同一天不重复；面试邀请、临近截止即时提醒 |
| 跟进 | 投递七天仍无回复提醒一次并准备草稿；发送由用户决定，间隔可调整 |
| 自动状态 | 明确申请确认、面试邀请、拒信可自动更新并显示邮件依据；模糊信息等待确认，不覆盖用户更正而不提示 |
| 长期记忆 | 保存明确档案、岗位记录、行动和已确认约定；重要事实变化由 Master 提议更新，不把每句聊天当长期事实 |
| 运行范围 | 电脑开机、后台运行；电脑关机继续运行和手机提醒后续扩展。休眠/离线期间不能保证实时，恢复后同步补查 |
| 学习方式 | 开发优先；关键选择解释原因/代价/替换路径；阶段结束提供可选 5–10 分钟讲解，无需独立学习 agent |

长期希望覆盖绝大多数申请网站，但第一版只承诺选定网站，无法处理时保留材料并交接用户。尚未做网站兼容性、服务条款或 OAuth 集成可行性核查，不能承诺具体网站的自动填写已可用。

## 复用审查（依据现有源代码）

| 现有部分 | 处理 | 判断和必要调整 |
|---|---|---|
| Electron/React 外壳、主题、语言、错误面板 | 保留并改首页 | 不再以项目管理表单/任务队列为首页；主视图是 Master + 求职看板 |
| `store.ts` 本地聊天、草稿、空间隔离 | 保留存储基础，调整交互 | 当前按聊天组织、仅最近 20 条完成消息且约 20k 字符进入上下文；持续对话不等于无限上下文，必须从结构化记录重新装配背景 |
| `codex.ts` 模型协议、流式和取消 | 有条件保留 | 作为可替换推理适配器；现有文本工具禁用策略不能直接支持 Gmail/浏览器操作。新工具由应用明确授权，不让模型文本扩权 |
| `project-input.ts` 与消息/任务快照 | 保留来源机制 | 输入改为求职档案、当前岗位、相关邮件/待办和已确认事实；本机路径/凭据不进入模型。邮件与网站内容只作资料，不是指令 |
| `memory.py`、`context_service.py` | 保留事件/版本/来源能力 | 用于已确认约定和补充背景；不能把关键词检索的记忆列表当岗位数据库或状态真相 |
| `task-store.ts`、`task-worker.ts`、`task-service.ts` | 保留生命周期基础，增量扩展 | 请求去重、持久化、取消、后台执行可复用；求职实体要有独立结构，不能硬塞 prompt/result/context_json |
| `task-scheduler.ts` 与每日入队记录 | 部分复用 | 目前仅入队且不调用模型；新产品要求经过明确授权后自动执行只读整理/分析。需分离同步、简报、提醒任务，增加执行/通知去重、离线恢复与失败反馈，不能直接改为自动跑全部旧队列 |
| `task-master.ts` 规划/1–3 子任务/总结 | 暂不作为用户入口 | 这是一次性顺序角色流程；用户要的是持续助理，不需要每条消息都走 3–5 次调用。只有真实独立子任务需要时才用 |
| 项目交接/历史/版本冲突 | 复用底层思想，弱化术语 | 求职主界面不要求用户管理项目版本或手工写交接；保留来源、历史和冲突保护，已有数据不自动迁移/删除 |
| 文件提案 Apply/Undo、目录授权、语法检查 | 冻结保留 | 保留旧入口与测试基线，退出求职主线；不能把 JS 单文件写入直接当简历编辑或浏览器提交能力 |
| 独立运行时打包与版本检查 | 保留 | 正式分发仍待许可证、签名、安装更新、干净机器及迁移验收 |
| OneDrive、IAM、通用执行、多层并行 agent | 暂缓 | 保护原代码/数据；不以“通用平台以后可能用到”为理由扩大第一版 |

## 需要新增的最小业务结构

- 求职档案：简历版本、硬条件、偏好、确认状态与来源。
- 岗位/申请记录：公司、岗位、发现链接、申请链接、阶段与时间、结束原因、匹配理由与档案版本、待确认标记；不只一段自由文本。
- 邮件与资料关联：来源消息 ID、原邮件链接、相关岗位、事件时间、证据及人工更正；去重不能只靠标题或公司名。
- 待办：岗位、行动、截止日期、优先级、来源、完成/推迟状态；界面与 Master 读同一份数据。
- 审核/填表状态：待准备、待用户检查、等待用户提交、已确认提交、状态不明；必须有确认依据才进入已投递。
- 通知与处理记录：本地日期简报收件箱、通知尝试、成功/失败、去重标识、补发状态；Windows 横幅未显示不等于任务未处理，软件内需可查。

这是业务设计，不是要求立刻拆多个服务、数据库或新框架。优先在现有应用内做小而完整的增量。

## 建议实施顺序与验收门槛

1. **静态但可操作的求职界面与数据模型**：合成岗位/邮件/待办 + Master 并排；选岗位带入上下文；可更正状态。验收能直接查材料、进度和下一步。先让用户确认界面再接真实数据。
2. **初始资料与 Gmail 只读闭环**：可审核导入旧资料、最近三个月邮件、岗位关联去重、证据和不确定状态。真实 Gmail 授权及用户资料接入单独执行，本次未读取。
3. **后台日常闭环**：只读增量同步、今日行动、10 点简报补发、面试/截止提醒、七天跟进；测试重启、离线、重复邮件、改期和失败。区分“已生成简报”“已尝试通知”“用户已看见”。
4. **主动发现与材料准备**：用户链接和岗位发现，基于已确认条件给理由；准备简历、跟进和面试材料。网站接入先做能力核查，小范围支持，失败清楚交接。
5. **选定网站辅助填写**：独立浏览器适配与明确人工提交边界；登录/验证由用户接手，失效恢复不重复投递。不把所有网站支持作为首版门槛。

先不选新 agent 框架。优先交付上述闭环，再依据真实分工决定是否增加子 agent。旧通用文件流程的验收不再是求职版开发前置条件。

## 实施前需要由具体方案解决的问题

不是再次开放产品范围：同步频率和“临近截止”的默认时间；10 点前开机时是否立即生成首份简报；初始历史邮件不逐封触发过期通知；截止日期时区与不完整时间；邮件误归类/错误合并的撤销；等待用户提交后如何确认真实结果；登录授权与本机数据备份；简历实际格式及无损编辑方式。这些应在对应里程碑给出合理默认与可审核方案，不一次性抛给用户。
